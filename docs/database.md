# Database

DoomVault stores operational data in SQLite and dossier narratives in JSON files. The database holds identities, authorization data, security settings, and dossier metadata. Authentication behavior is described in [authentication.md](authentication.md).

## Location

The default database path is `instance/doomvault.db`. Set `DOOMVAULT_DATABASE` to override it. Relative paths are resolved inside Flask's instance directory. Absolute paths are used unchanged, which is how the tests point at a temporary file.

`flask --app app init-db` creates missing tables and indexes and applies the supported legacy schema updates without deleting existing rows. Task2.2 rebuilds the legacy permission/status tables transactionally to extend their CHECK constraints, preserving primary keys, references, data, indexes, and triggers.

`flask --app app seed-db` requires those tables. It inserts missing catalog data, accounts, settings, the initial forbidden-word dictionary, and dossier metadata without replacing existing rows. Default grants are added only for new roles or permissions. Manually removed role-permission grants stay removed on subsequent runs, and custom grants are kept. Other removed default catalog rows are inserted again. Existing account assignments and settings are preserved. After its one-time installation marker is stored, the forbidden-word dictionary is fully administrator-managed: additions, edits, deletions, and an intentionally empty dictionary survive subsequent seed runs.

## Connections

`database.py` opens SQLite with Python's `sqlite3` module. Each connection:

- uses `sqlite3.Row` so results can be read by column name
- runs `PRAGMA foreign_keys = ON` before any application query
- is stored on Flask's application context and closed when that context ends

Queries that include variable values use parameter placeholders. Multi-row seed writes run in one transaction and roll back if any statement fails. Timestamps generated by the application are UTC strings in the form `YYYY-MM-DDTHH:MM:SSZ`.

There is no general migration framework. Supported authentication/session updates run on connection; the Task2.2 constraint upgrade runs explicitly through `init-db`. It temporarily disables foreign-key enforcement outside the migration transaction, rebuilds only the affected tables, checks all foreign keys before commit, and restores enforcement even after rollback. Run `init-db` then `seed-db` for an existing Task2.1 installation. Unexpected columns or invalid references stop the upgrade instead of silently discarding data.

## Tables

### roles

The five application roles: `administrator`, `manager`, `editor`, `employee`, and `reader`. `name` is the stable identifier. `description` includes the display name and a short statement of responsibility.

### permissions

The thirteen named permissions, including `dossiers.read_doom_level`. Ownership permissions such as `dossiers.edit_own` are enforced alongside ownership/lifecycle helpers. See [rbac.md](rbac.md).

### role_permissions

Composite primary key of `role_id` and `permission_id`. A role receives only the grants listed in [rbac.md](rbac.md).

### users

One row per person. `username` is unique under case-insensitive comparison, so `ADMIN` and `admin` cannot both exist. `password_hash` stays null until a permanent Argon2id hash is stored. `role_id` is required. `is_active`, `is_blocked`, and `must_change_password` are integers restricted to 0 or 1.

Seeded accounts are created with `password_hash` null, `is_active` 0, `is_blocked` 0, and `must_change_password` 1. `password_changed_at` stays null. `is_blocked` marks an account that `provision-user` must not reactivate. `is_active` 0 with `is_blocked` 0 means the account is still waiting for its first temporary credential. Databases created before this column receive it on the next connection.

### password_history

Stores previous Argon2id password hashes. The application keeps the newest rows up to `password_history_limit` and rejects those passwords during a later change. The hash column cannot be empty. No history rows are created during seeding.

### temporary_passwords

Stores an Argon2id hash, a creation time, an expiry time, and the time the temporary password was used. Plaintext passwords are never written here. The lifetime is `temporary_password_validity_hours`, which is 12. `provision-user` creates these rows. A row with `used_at` set cannot be used again.

### sessions

Server-side sessions. `session_token_hash` is the SHA-256 digest of the cookie value and cannot be empty. `credential_kind` is `password` or `temporary`. `temporary_password_id` reserves the temporary credential that opened the session. `role_id_at_creation` records the server-side role context; a changed or missing context requires fresh authentication. `revoked_at` marks a logged-out, rotated, or expired session. `last_activity_at` and the rolling `expires_at` deadline are checked before renewal; there is no separate absolute lifetime. See [session_management.md](session_management.md).

### forbidden_words

The editable denylist used by the password policy. Before insert, a word is stripped and casefolded, and internal whitespace is rejected. The normalized value is unique. The seed list contains organization words, English month and season names, and the Polish season words `wiosna`, `lato`, `jesien`, and `zima`.

`data/wordlist.txt` is the word source for temporary passwords. It is separate from this table. The live forbidden-word dictionary remains here so a later administrator screen can edit it.

### settings

One row per configuration key. Values are text. Integer settings use decimal text, and the boolean setting uses `true` or `false`.

| Key | Initial value | Meaning |
| --- | --- | --- |
| `minimum_password_length` | `14` | Minimum length for a permanent password |
| `forbidden_words_enabled` | `true` | The forbidden-word rule starts enabled |
| `temporary_password_validity_hours` | `12` | Lifetime of a temporary password |
| `password_history_limit` | `5` | Number of previous hashes to reject for reuse |
| `session_inactivity_timeout_minutes` | `15` | Inactivity window applied to a session |
| `password_validity_days` | `0` | `0` disables periodic password expiration |

The internal `forbidden_words_seed_version` marker records completion of initial dictionary seeding. It is not an administrator-configurable policy. Once present, repeated seeding never recreates dictionary entries that an administrator deleted.

A value of `0` for password validity means permanent passwords do not expire on a schedule until that value is raised. There is no settings screen yet. Temporary passwords use three randomly selected words followed by two digits.

### dossiers

Metadata for a JSON dossier. `id` is a stable identifier such as `DV-001`. `file_name` must be that identifier plus `.json`, so the column cannot store a user-supplied path. `created_by` and `approved_by` reference `users` and are null for the seeded archive because those inactive accounts did not author the files.

`organization` is `SHIELD`, `HYDRA`, `SWORD`, or `UNKNOWN`.

`classification` is `DECLASSIFIED`, `INTERNAL`, `SECRET`, `TOP_SECRET`, or `DOOM_LEVEL`. `DOOM_LEVEL` is a classification label, not a role.

`status` is `DRAFT`, `PENDING`, `SUBMITTED`, `APPROVED`, `REJECTED`, or `DECLASSIFIED`. `PENDING` is the Task2.2 review state; existing `SUBMITTED` rows retain their value and equivalent access policy. No workflow endpoints are introduced.

### incident_reports

Reserved for incident reports submitted by employees. `created_by` references `users`. No reports are seeded.

### security_events

A basic event log. `user_id` may be null for an event that is not tied to an account. Descriptions must not contain passwords, password hashes, session tokens, or other authentication secrets. Failed sign-in attempts record `login_failure` and a hash of the normalized username. Session lifecycle operations record `session_created`, `session_expired`, `session_revoked`, and `session_logout`. Task2.2 records one `authorization_denied` event per denied request, with the current user ID and a server-defined operation. Routine activity and successful permission checks are not logged.

## Relationships

Foreign keys use `ON DELETE RESTRICT`. A role or user referenced by another row cannot be deleted until the dependent rows are removed deliberately.

- `users.role_id` references `roles`
- `role_permissions` references `roles` and `permissions`
- `password_history`, `temporary_passwords`, and `sessions` reference `users`
- `dossiers.created_by` and `dossiers.approved_by` reference `users`
- `incident_reports.created_by` and `security_events.user_id` reference `users`

Indexes cover role lookup, dossier organization, classification, and status, session expiry, password history by user and time, and security events by user, type, and time.

## Dossier files

Narrative content lives in `data/dossiers/DV-001.json` through `data/dossiers/DV-008.json`. Those files are application data outside Flask static storage. Task2.2 reads them only through authorized dossier routes; direct file URLs return 404. Seeding and retrieval validate document structure, and SQLite remains authoritative for access-control metadata.

```json
{
  "id": "DV-003",
  "title": "Sokovia Incident",
  "organization": "SHIELD",
  "classification": "SECRET",
  "status": "APPROVED",
  "incident": {
    "location": "Sokovia",
    "threat_level": "CRITICAL",
    "summary": "A fictional intelligence summary describing the incident.",
    "observations": [
      "Observation one",
      "Observation two"
    ],
    "conclusion": "An original fictional assessment of the incident."
  }
}
```

`threat_level` is one of `LOW`, `MODERATE`, `HIGH`, `CRITICAL`, `EXTREME`, or `UNKNOWN`. The database row copies `id`, `title`, `organization`, `classification`, `status`, and the stable file name. The incident narrative stays in the JSON file.
